# 《魔镜 Online》还原路线与资源评估

核查日期：2026-11-14。本文是建议方案，不替代用户已拍板的决定，不代表已实施目录迁移或玩法改动。

## 最重要的判断

继续沿用当前 Godot 主线。最快接近原作的办法，是先把遗迹之岛的一段十分钟体验做完整、做像，再沿用同一套组件扩展世界。

把工程想成复建一座老游乐园：资料库是旧照片；JSON 是设施清单；Godot 是新地基与传动装置；美术是门面和布景。目前传动装置已经能转，布景和游客游览路线还没有接起来。设施清单很长，不等于设施已经造好。

“全游戏还原”有三个不同终点：

- 外观还原：构图、角色比例、场景、窗口、字体与特效接近截图。
- 单机体验还原：自己能创角、做任务、打怪、捡物、换装、跨图、保存进度。
- 在线世界还原：多人同步、组队、公会、交易、国战，以及服务端结算与持久化。

建议先完成第二个终点，同时逐段验收第一个。第三个需要独立工程阶段，不能用假玩家和空面板算完成。没有原始文件或足够证据的部分，只能做有标记的近似还原。

## 一、当前进度：以代码和实测为准

### 已经存在

- 游戏本体在 `game/`，本机实际引擎为 Godot 4.7.2。
- 点击地面寻路、点击怪物靠近普攻、Tab 选最近目标、相机居中。
- 怪物追击/攻击/回位、玩家受伤与闪避、死亡后延时复活。
- 击杀经验、升级、六职业射程与伤害类型配置、脱战自动回复。
- HUD、地形、冒烟脚本已经从世界根脚本分离；“还完全没拆代码”的说法过期。
- 14 张数据表可加载并校验。表内有 6 职业、150 级条目、50 装备和 106 NPC。

### 本次重新验证

1. `python game/tools/validate_data.py`：14 表，0 错误。
2. Godot `--smoke-nav`：直线 980px，绕行 1064px，5 个拐点；到达误差 1px，终点不在障碍内。
3. Godot `--smoke-rest`：3 秒仍处战斗，7 秒开始休息；13 秒血量 168/228，蓝量 70/102。

这些测试证明当前配置下的局部行为。本次没有重跑全部职业、全部地图、浏览器交互、长时间性能或完整死亡流程，不据此声称全项目无 bug。

### 还没有完成

- 地图是网格和生成的岩石障碍；角色和怪物仍为占位图形。真实地形、八向动作、遮挡尚未组成原作画面。
- 还没有玩家可操作的创角选职业流程；命令行选择职业不等于创角完成。
- 技能、掉落、背包装备、任务交付、传送、存档等没有在 Godot 中形成完整体验。
- 原版 HUD 和正式面板资产尚未真正装入当前游戏；`game/assets/` 当前主要是字体。
- 地图/装备/NPC/任务有表，不等于对应系统已经能玩。

### 资料数量不等于还原程度

校验器统计状态标记：已定 16、图证 216、推定 469、未判定 5，共 706 处。它们是状态标记数量，不是相互独立的全部事实数量，也不是完成度。

`quests.json` 明确注明 108 条任务由规则生成，名字、文本无图证；`skills.json` 是占位技能。50 件星空装备主要覆盖高等级，不能直接补齐 1–10 级装备链。缺的新手装备和掉落规则应单独标记推定。

## 二、最影响速度和还原度的五个问题

### 1. 文档有冲突，会让 AI 在已做过的事上反复劳动

- README 已说明 `docs/14` 过期；`docs/20` 却仍有“怪不还手、人不会死”等旧结论。
- README 写“考据像素不进游戏”；旧决策 D-06 与 `docs/art/08` 又允许保留正确原像素、使用考据图派生件。
- 284、301、338 来自不同批次、筛选与去重口径，不应混为一个资产总数。

建议：README 只保留当前入口；增加一份当前约束清单，每条带决策编号与日期；旧文件标明历史。素材规则冲突应追溯最新用户原话后定稿，不能按文件位置自行覆盖。事实台账、候选素材清单、可用资产清单分开统计。

### 2. 数值和角色状态还分散在不同地方

`monster_field.gd` 当前 502 行，同时管理刷怪、选中、普攻、经验和职业；等级、经验也存在怪物场里。换地图时如果重新建场景，后续容易丢失进度。普攻间隔 0.55 秒等配置仍在脚本中，未完全做到“数值只有一个家”。

建议：先抽 `GameSession` 保存角色职业、等级、经验、货币、任务和背包；再随功能增加 `CombatService`、`InventoryService`、`QuestService`。现有公式、寻路和 HUD 保留。按真实边界拆，不为行数而拆，不引入大型通用框架。

### 3. 地图坐标缺少真实标定

世界根脚本按 NPC 最大坐标推地图尺寸，再乘固定 32px；这可以支持占位测试，不能证明是原作尺度。

每张图应有：原作坐标到世界像素的换算、边界、出生点、传送点、不可走区与遮挡层。用三个以上可辨识地标检查换算；底图和碰撞分离。小地图放大只能做已批准的占位图，放大不会恢复原版地形细节。可以用底图加独立物件，不必强行改成瓦片地图。

### 4. 视觉验收排得太晚

等全部系统写完才比较画面，会在错误比例上积累大量美术。

现在就选一张目标版本截图，固定分辨率、相机、缩放、站位与 HUD，做半透明叠图对照。先查人物高度、脚底位置、地物比例、窗口边距和字体，再看细节。半透明底色和遮挡推补应标估计，不能声称从单张截图唯一恢复。不要用一个“相似度百分数”掩盖明显错位。

### 5. 外部项目容易让主线分叉

本地 `resources/third-party/mojing-online` 的远程指向另一份魔镜重制项目，不是 2011 年原版源码。README 描述创角、WebSocket、存档等，但本地目录缺少它引用的 `_archive/legacy-web-layout/server/` 与 `docs/handoff/`，不能直接认定完整可运行。

处理方式：读它的客户端流程、界面和公开交接记录，逐个比较后移植思路。不要把 PixiJS/TypeScript/WebSocket 客户端直接塞进 Godot，也不要把它推定的任务/数值升级为原作证据。

## 三、推荐结构：资料仓库 → 组件工厂 → 游戏 → 对照验收

保留现有四层素材归档，不大搬家。建议职责如下，新增目录只在对应功能开工时建立：

```text
docs/                 当前约束、原作事实、推定值、任务验收
resources/art-library/          原图 → 提取信息 → 切片 → 候选复刻件
assets/               验收后的资产及来源清单
game/
  _archive/legacy-web-layout/data/               唯一运行数值；保留状态与来源
  assets/             游戏实际引用的 PNG、声音、字体
  scenes/
    actors/           角色、怪物、NPC 场景
    maps/             地图、传送、遮挡
    ui/               HUD、背包、任务、创角
  scripts/
    core/             数据读取、公式、寻路
    session/          跨图保留的角色状态、序列化
    systems/          战斗、掉落、装备、任务
    world/            场景装配、实体行为、地图交互
  _archive/legacy-web-layout/tests/              可自动判定成败的行为检查
  build/              导出结果，不手工维护
resources/third-party/           外部参考，不能成为第二套运行真相
```

素材清单至少记录：来源图、裁切区域、候选/已验收/已入游戏、目标尺寸、透明度、锚点、动画方向/帧率、授权或来源限制。对规则记录版本/地区，避免大陆和台服不同时期资料混用。

存档仍按现有决定本期不实现，但 `GameSession` 要能转成普通数据；将来接存档或服务器不必重写所有窗口。多人阶段由服务端负责结算伤害、物品与货币，界面仅提出操作请求。

根目录本次未见 `.git`。建议建立当前 Godot 主线的版本记录，忽略 `.godot/`、导出包和临时产物；原始素材独立备份。外部参考项目的 `.git` 不能保护当前游戏。

## 四、推进顺序：每段都有一个看得见的成品

这是建议的验收顺序，不是日历工期承诺。保留既定“掉落 → 拆代码 → 创角 → 底图 → 传送 → 背包”主线，在开工时加入小型视觉对照。

### 第一步：一个稳定的样板画面

先确定目标版本、目标截图与固定画面尺寸，核对素材政策。给现有骨架接一个最小 HUD 和静态角色/场景样板，确认比例。完整底图仍按已批准的示意图占位方案推进，不把它当最终美术。验收：原图与重制画面能在同尺寸下直接对照，差异有清单。

### 第二步：掉落、状态归属、创角

一个怪物死亡生成一件测试掉落；先用最小拾取容器，不提前做全量背包 UI。缺图证的掉落率明确标推定。抽出跨图角色状态；六职业可以从界面选择；先精修一个职业的外观。验收：所选职业影响射程，击杀后物品确实进入角色状态。

### 第三步：一张图与一个出口

完成遗迹之岛的占位底图、坐标换算、碰撞与遮挡；出口连到第二张测试图。验收：点击能绕路，地物不穿帮，跨图保留等级/血蓝/物品；等级门槛按表执行。

### 第四步：十分钟可玩的原味样板

补最小背包/装备、一个 NPC、一条任务、一个技能槽与对应反馈。使用已有图证；无资料的内容显示明确占位。验收：选职业 → 接任务 → 寻路 → 打怪 → 掉落 → 拾取 → 换装 → 交任务 → 升级 → 传送。

技能名字缺证据，不应阻塞耗蓝、冷却、目标判定这些机制；先用“技能格01”验证机制，但不虚构原作名称和效果。

### 第五步：把样板扩成全世界

先扩新手 1–10 级体验，再扩地图、怪物、任务与装备；后接天赋/转职/副本。每扩一批复用样板组件并检查证据。公会/邮件空壳按旧计划可保留，但不计为真实功能完成。多人、交易、国战另立阶段。

动画若最终要八向，文件和方向接口现在就按八向设计；前期允许缺帧占位，避免把镜像四向当作最终八向。不要一次生成六职业全部动作，先通过一个角色的待机/行走/攻击/死亡样板。

## 五、真正有用的 AI Skills 与工具

下面的外部资源已于核查日查看项目页；能力以项目说明为据，尚未安装或做兼容性验证。

### 现在优先

1. [fetasty/godot-skills](https://github.com/fetasty/godot-skills)：优先挑 `godot` 和 `godot-gdscript` 两项，帮助 AI 处理场景、信号、类型和脚本结构。仓库说明以 Godot 4.6 为目标，本地 4.7.2 的接口必须再对照对应文档，不能照单全收。
2. [bradypp/godot-mcp](https://github.com/bradypp/godot-mcp)：让 AI 启动项目、取得日志、编辑场景节点。Skill 像施工说明书，MCP 像可以拿工具操作的手。当前命令行已能做部分验证；先试运行/读日志，再考虑场景操作。它不自动保证画面还原，也不能假定具备任意视觉交互验证。
3. 项目专用“原作证据核对”技能：建议定制。每次改动先查目标版本、原图、决策；字段附来源和状态；看不清写缺失，不补故事。这比泛用“帮我做 RPG”提示更贴合本项目。
4. 项目专用“素材入库与对照”技能：建议定制。固定尺寸、RGBA、锚点、方向、帧率、命名；产出原图/候选/组装结果三联对照；验收后再进游戏。已有 image-to-svg 只用于合适的平面图形，手绘角色和有纹理 UI 保持 PNG；imagegen 用于有参照的缺口补绘。
5. 项目专用“单任务交付”技能：建议定制。每次只实现一个可验收动作，交付运行入口、截图、行为结果和未定项。现有冒烟脚本继续用；逐步增加失败断言和非零退出码，避免只打印日志却总显示成功。

Skill 是 AI 的工作规程，不是原作数据库；没有原图和原始包，安装再多技能也不会长出原版素材。上述三项项目专用技能是建议名称，本轮未创建或安装。

### 功能扩展时再用

- [GdUnit4](https://github.com/godot-gdunit-labs/gdUnit4)：适合物品堆叠、换装重算、任务只发一次奖等可精确判定的问题。按兼容表选择并锁定版本，本机 4.7.2 仍需实测。它不代替画面验收。
- [Godot Dialogue Manager](https://github.com/nathanhoad/godot_dialogue_manager)：维护 NPC 分支对话。当前项目页说明 v4 支持 Godot 4.6+。只有简单领取/交付时，可先直接用表驱动，不必急着增加插件。
- [LimboAI](https://github.com/limbonaut/limboai)：给复杂 BOSS 行为树与状态机使用。当前追击、攻击、回位已经存在，不值得为了安装它重写；以后需验证 Web 导出和二进制兼容。
- [Godot 官方示例](https://github.com/godotengine/godot-demo-projects)：取动画、UI、导航等局部做法；按引擎版本选示例，不复制整款陌生游戏框架。
- [GDQuest Learn GDScript](https://github.com/GDQuest/learn-gdscript)：给零基础用户学习最少概念。先理解场景/节点、信号、数据表和运行日志，足以描述验收与识别 AI 是否交付，暂时不必从头学完整引擎。
- [awesome-gamedev-agent-skills](https://github.com/gamedev-skills/awesome-gamedev-agent-skills)：用于检索缺少的专长，避免整包叠加多个互相冲突的 Godot 总管技能。

## 六、素材和原始资料：优先级决定还原上限

### 第一档：本作原始文件，价值最高但尚未取得

现有 `docs/research/extra/E4` 已记录原官网/客户端调查无收获。后续只补明确新增线索：老玩家浏览器缓存、微端备份、旧硬盘、台服发行渠道、网页存档及 Flashpoint 目录。不应重复扫描同一批失效网址。

- [Flashpoint Archive](https://flashpointarchive.org/)：可检索网页游戏保存目录。未确认收录《魔镜 Online》，不能承诺有下载。
- [JPEXS FFDec](https://github.com/jindrapetrik/jpexs-decompiler)：拿到 SWF 后提取其中的图像、声音、形状和脚本；空有工具不能提取不存在的文件，也可能还缺外部资源。
- [Ruffle](https://github.com/ruffle-rs/ruffle)：有 SWF 后尝试播放、考据动作；它不会恢复已停运的游戏服务器。

为原始包调查设一次明确的短期时间盒，记录来源、结果、下一条线索。没有新增线索时继续做样板，不让全项目停在无限搜集阶段。

### 第二档：本地已经有的候选和截图

优先复用已切割、精修的 UI 与已有读图台账，继续核验来源与组装效果。台账称 284 张已逐张读完，本次没有重新逐张复核所有原图；不能将旧台账视为本次新完成的读图。

原图小尺寸是验收基准。放大/去噪适合辅助观察，不会恢复真实细节；AI 新生成的字、装备纹样和被遮挡背景均不能升级为“图证”。

### 第三档：其他开源素材，只填机制占位

本地已有 [pixelfx](https://github.com/patch-gg/pixelfx)：可以导出序列帧供 Godot 使用，适合先接上命中、拾取、传送反馈。其像素风与本作低分辨率手绘不同，直接大规模铺用会降低原味；先选一项在原尺寸下比较。仓库说明代码与特效为 MIT，字体另有通知。

其他游戏的角色、现成 MMORPG 模板、通用像素素材可以帮助测试机制，不能替代本作美术考据。开放源码不代表其中所有图片都能任意再分发，采用时逐项保留来源和许可。

## 七、零基础用户怎样指挥 AI

你负责挑目标图、指出“不像”的位置、验收能否完成动作；AI 负责查资料、落实代码和复现测试。

一次任务交代四件事：

1. 对照哪张图、哪个版本，哪些用户决定必须遵守。
2. 本轮只新增一个什么动作，例如“点怪死后，走近捡到一件物品”。
3. 怎样算通过，例如“只入账一次；背包满有提示；换地图不丢”。
4. 交付什么，例如“可运行入口、原尺寸前后对照、检查结果、缺证据列表”。

可直接使用的任务口径：

> 继续 Godot 主线，遵守 README 当前决定与最新用户原话。本轮只完成遗迹之岛的一项可验收功能。先说明已有代码和可复用素材，列出会改哪些文件；有证据的照证据，无证据的标推定。做完运行验证，提供可操作入口与原尺寸截图，说明仍缺什么。不要把“有数据表”“有空面板”写成玩法已完成，不更换引擎，不批量现代化美术。

最快的下一轮工作包：先核对素材规则冲突并建立一张固定对照图；接最小掉落，抽出角色状态，按既定顺序进入创角和底图。每轮留下一个可以打开、可以比较、可以操作的成果。
